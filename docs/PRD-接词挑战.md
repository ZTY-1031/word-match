## 1. 玩法理解

### 1.1 一句话定义

两名玩家在互相看不见对方输入的前提下，就同一个「锚点词」各自写下一个词；两词不同则这个分歧成为下一轮的锚点继续往下接，两词相同则本局挑战成功。

### 1.2 玩法本质

这不是对抗游戏，是**合作型的默契博弈**。玩家共享同一个胜利条件，敌人是「信息不对称」本身。

三个心理机制同时起作用，这是它能成立的原因：

1. **共识收敛**：双方都倾向于写「最显而易见的那个词」，所以越常规的思路越容易撞上，游戏奖励「站在对方视角思考」。
2. **分歧扩散**：一旦某一轮出现分歧，两个不同的词各自衍生出不同的联想分支，共识被稀释，后续撞词难度上升。游戏因此天然有一条「先易后难」的张力曲线。
3. **信息泄露的诱惑**：历史词公开，等于双方在不断暴露自己的联想习惯，玩家可以逐步「建模」对手。这是策略深度的来源。

所以规则设计的核心不是「让人猜得准」，而是**控制信息暴露的节奏**。

### 1.3 一局游戏的完整时间线（15 轮上限，20 秒/轮）

起始锚点：`夏天`

| 回合 | 玩家 A | 玩家 B | 判定 | 下一轮锚点 |
| --- | --- | --- | --- | --- |
| 1 | 西瓜 | 冰棍 | 不同，继续 | 西瓜 / 冰棍 |
| 2 | 空调 | 蝉 | 不同，继续 | 空调 / 蝉 |
| 3 | 热 | 热 | **相同，成功** | — |

结算：3 轮撞词，评级 S。

第 3 回合是关键：双方从「空调」和「蝉」这两个发散分支里，同时回到了「热」这个共同的上位感受——这是游戏最爽的时刻，结算页要重点渲染。

### 1.4 机制上必须先钉死的四个空洞

原始描述没定义这四处，不补实现出来会立刻崩：

1. **能不能抄对方上一轮的词？** 能的话第 2 回合必撞，20 秒结束。→ **禁止本局任何历史词复用**（见 2.8）。
2. **「接词」要不要强校验语义相关？** 强校验需语义模型，误判会毁局且引发规则争议。→ **不校验，只展示锚点**（见 2.2）。
3. **双方同时提交，谁权威？** → **服务端权威状态机**，客户端只是投影（见第 5 章）。
4. **两人同一轮都超时，算不算「撞」？** → **`null` 与 `null` 判定为不相同**，否则双挂机能白嫖胜利（见 2.5）。

## 2. 游戏规则

### 2.1 角色与目标

| 项 | 定义 |
| --- | --- |
| 玩家数 | 固定 2 人，无观战位 |
| 阵营 | 同一阵营，共享胜负 |
| 胜利条件 | 任意一回合双方提交的词归一化后完全相同 |
| 失败条件 | 达到回合上限仍未撞词 / 主动放弃 / 房间异常关闭 |

### 2.2 回合机制

**锚点（Anchor）**：每回合双方可见的共享参照物，是「接词」的落点。

- 第 1 回合锚点 = 系统给定词（默认取自内置主题词库随机，房主可自定义或选「无锚点」）。
- 第 n 回合（n ≥ 2）锚点 = 第 n-1 回合揭晓的**两个词**（并列展示，形如 `西瓜 · 冰棍`）。
- 锚点只做展示与联想引导，**不做语义校验**。玩家写什么都可以，只要合法。

**回合流程**：

```
锚点展示 → 20 秒倒计时开始 → 双方各自私下输入
   → 双方均已提交（立即结算，不必等倒计时走完）
   → 服务端判定 → 同时揭晓双方词（动效）
   → 相同：结算成功 ／ 不同：两词并入锚点，进入下一回合
   → 若 20 秒到仍有人未提交：未提交方记弃权轮，同样立即结算
```

**[决策] 双方提交即提前结算。** 这是本轮确认的关键节奏点：不设「等待倒计时走完」的拖沓，实测绝大多数回合会在 8–12 秒内结束，整局体感从「一问一答」变成「抢答」。

**回合上限**：默认 15 轮，**房主建房时可自定义**（建议区间 5–50）。达到上限仍未撞词判「挑战失败」。

### 2.3 判定逻辑

判定发生在**服务端**，客户端不参与。

```
normalize(raw):
  1. 去首尾空白
  2. Unicode NFKC 归一（全角转半角）
  3. 去除内部所有空白字符
  4. 英文字母统一转小写
  5. 去除首尾标点（内部标点保留原样参与比较）
  → 返回 result

判定：normalize(A) == normalize(B) ? WIN : CONTINUE
特殊：任意一方为 null（弃权）时，一律判 CONTINUE，包括 null == null
```

**明确的判定边界**：

| 情况 | 是否算撞词 | 说明 |
| --- | --- | --- |
| `苹果` vs `苹果 ` | 算 | 首尾空白被归一 |
| `Apple` vs `apple` | 算 | 大小写归一 |
| `Ａ` vs `A` | 算 | 全角转半角 |
| `苹果` vs `苹果！` | 算 | 首尾标点被去除 |
| `西瓜` vs `西 瓜` | 算 | 内部空白被去除 |
| `苹果` vs `平果` | 不算 | 错别字不纠正 |
| `猫` vs `猫咪` | **不算** | 不做同义/近义判定 |
| `cat` vs `猫` | **不算** | 不做跨语言判定 |
| 双方均超时 | **不算** | 弃权轮永不判胜 |

**[决策] 不做语义等价判定。** 语义判定误判成本极高（把「猫」「猫咪」判相同，玩家会莫名其妙地赢；判不同又会被骂不智能），且引入不可解释的黑盒，破坏「双方完全一致」这条规则的确定性。**规则的确定性优于规则的人性化。**

### 2.4 胜负与结算

| 结果 | 触发 | 结算页方向 |
| --- | --- | --- |
| 成功 `WIN` | 某回合归一化后相同 | 「第 N 轮，你们想到了一起」+ 词链回顾 + 评级 |
| 失败 `ROUND_LIMIT` | 满 15 轮（或自定义上限）未撞 | 「差一点点」+ 高亮最接近的一轮 |
| 失败 `GIVE_UP` | 任一玩家主动放弃 | 「A 放弃了本局」+ 已产生词链 |
| 中断 `ABORTED` | 房间异常关闭 / 双方均离线超时 | 「本局未完成」不计战绩 |

**评级**（仅成功时）：默认上限 15 轮下，≤5 轮 S，≤10 轮 A，≤13 轮 B，其余 C。评级阈值按 `maxRounds` 等比换算，避免自定义轮数后评级失真。

**没有平局，也没有失败方**——两人同赢同输，结算页不出现「你输了」这类指向个人的措辞。

### 2.5 时间规则

| 计时项 | 值 | 可配置 | 说明 |
| --- | --- | --- | --- |
| 单回合输入时限 | **固定 20 秒** | 否 | 全局统一，所有房间一致 |
| 提前结算 | 双方提交即刻判定 | — | 剩余时间直接作废 |
| 揭晓动画 | 2 秒 | 可点击跳过 | 跳过仅对当前玩家生效，不阻塞他人 |
| 整局总时限 | 无 | — | 由回合上限兜底（15 轮 × 20s ≈ 5 分钟上限） |
| 房间空置回收 | Redis TTL 2 小时 | — | 无需额外回收任务 |

**超时处理**：

- 20 秒到期瞬间，服务端以「已输入内容」自动提交；输入框为空则记为**弃权轮**（值 `null`）。
- `null` 与任何值都不相等，因此该回合必然不撞，直接进入下一轮。
- **双方同时超时 = 本轮作废**，不判胜，直接进入下一轮，轮次照常消耗。
- **[决策] 不设弃权次数上限。** Demo 阶段由回合上限兜底（最坏 5 分钟必然结束），省掉一套计数与判负逻辑。代价是极端情况下有人挂机拖满 15 轮——10 人内部使用可接受，V1 再补。

### 2.6 历史词展示

| 内容 | 策略 |
| --- | --- |
| 自己的历史词 | 全部展示（进入词链） |
| 对手的历史词 | 每回合揭晓后进入词链，全部展示 |
| 当前回合对手的输入 | **不可见**，仅显示「已提交 / 思考中」 |
| 锚点词 | 展示 |

**[决策] 不做盲接模式，不做灵感提示，不做对手习惯分析。** 历史信息只保留「词链里已揭晓的双方词」这一种形态，没有任何额外提示层。理由：Demo 阶段功能越少越容易验证核心玩法是否成立；如果玩家必须依赖提示才能玩下去，说明玩法本身有问题，那也不该用提示来掩盖。

**词链**是唯一的历史载体：横向时间线，每轮一格，并列显示双方词与判定结果，可点击查看轮次详情。它是玩家的全部信息面。

### 2.7 放弃与退出

| 操作 | 入口 | 确认 | 结果 |
| --- | --- | --- | --- |
| 放弃本局 | 对局页右上角「⋯」 | 二次确认弹窗 | 立即结束，双方看到 `GIVE_UP`，标注发起人 |
| 关闭页面 / 返回 | 浏览器行为 | 无 | 视为离线，不立即结束（见 5.4） |
| 房主解散房间 | 等待页 | 二次确认 | 房间销毁，对手回首页并提示 |

- 放弃不可撤销。
- 双方几乎同时放弃：以服务端先到达那条为准，另一方收到「对局已结束」而非自己的放弃回执。
- 放弃的对局不计战绩、不生成分享。

### 2.8 词条合法性规则

| 规则 | 定义 | 违规处理 |
| --- | --- | --- |
| 长度 | 中文 1–12 字；纯英文 1–20 字符；混合按字符数 ≤ 16 | 输入框实时提示，禁止提交 |
| 字符集 | 中文、英文字母、数字。**不允许**空格、标点、emoji、特殊符号 | 输入时过滤，无法输入 |
| **历史词复用** | 归一化后与本局任何一方已出现过的词相同 | 提交被拒，提示「这个词本轮之前出现过」 |
| 空值 | 空字符串 | 不可提交（等同等待超时） |
| 敏感词 | **不做过滤**（Demo 取舍，见第 10 章） | — |

**[决策] 禁止历史词复用是硬约束，不可配置。** 它堵死一个致命漏洞：允许复用的话，玩家第 2 回合直接抄对手第 1 回合的词即可 100% 撞词，游戏在两回合内失去意义。副作用是正面的——强制玩家每轮都想新东西，维持了张力曲线。

### 2.9 边界情况处理表

| 场景 | 处理方式 | 用户可见反馈 |
| --- | --- | --- |
| A 已提交，B 迟迟不提交 | 20 秒到 → B 记弃权，立即结算 | A 看到「对方还在想⋯」，倒计时环收尾 |
| 双方同一毫秒提交 | 服务端按房间串行处理，后到者触发判定 | 无异常，正常揭晓 |
| 双方同时超时 | 本轮作废，不判胜，进入下一轮 | 「两个人都在发呆」 |
| 提交瞬间断网 | 客户端保留输入，重连后自动重发 | 「网络波动，正在重连」 |
| 重复提交（重试/连点） | 按 `(roomId, playerId, roundNo)` 幂等去重 | 无感 |
| 对手中途断线 | 回合不暂停，照常计时 | 「对方掉线了」 |
| 断线 30 秒内重连 | 拉快照，恢复当前回合与剩余时间 | 「已重新连接」 |
| 断线超过 30 秒 | 在房玩家可选「继续等待 30 秒」或「结束本局」 | 二选一弹窗，超时默认结束 |
| 双方同时离线 | 房间冻结，2 小时后 Redis TTL 回收 | 重进可恢复 |
| 刷新页面 | 携 token 恢复，等同重连 | 直接回到对局 |
| 同一账号多标签页 | 后开标签接管，旧标签降级只读 | 「已在其他窗口进行」 |
| 满员后第三人进入 | 拒绝 | 「房间已满（2/2）」 |
| 房主在等待页退出 | 房间销毁 | 对手回首页 |
| 撞词发生在最后一轮 | 判 `WIN` 优先于 `ROUND_LIMIT` | 正常成功结算 |
| Redis 重启 / 服务重启 | 进行中对局丢失，房间可恢复但需重开 | 「对局已失效，请重新开始」 |
| 自定义 `maxRounds` 为 1 | 允许，但提示「大概率一局定胜负」 | 前端校验下限 1 |

## 3. 核心玩家流程与页面构成

### 3.1 主流程

```
① 落地页（玩法介绍 + 开始）
      ↓
② 创建房间（设置上限轮数/起始锚点）──→ ③ 等待页（房间码/邀请/准备）
      ↑                                        ↓ 双方就位
      └── ④ 加入房间（链接/房间码）←────────────┘
                                               ↓
                                        ⑤ 对局页（20s 回合循环）
                                               ↓
                                        ⑥ 揭晓动效（每轮内嵌）
                                               ↓
                                        ⑦ 结算页 ──→ 再来一局 / 回首页
```

### 3.2 页面清单（Vue 路由）

| # | 页面 | 路由 | 核心元素 |
| --- | --- | --- | --- |
| P1 | 落地页 | `/` | 一句话玩法、动图演示、`创建房间` 主按钮、`加入房间` 次按钮、规则入口 |
| P2 | 建房设置 | 弹层（不占路由） | 回合上限（默认 15）、起始锚点（随机/自定义/无） |
| P3 | 等待页 | `/room/:code` | 房间码大字、复制链接、二维码、两个席位、`开始游戏` |
| P4 | 对局页 | `/room/:code/play` | 顶部回合进度 + 20s 倒计时环 + 对手状态；中部锚点 + 词链；底部输入框 + 提交 |
| P5 | 揭晓层 | P4 内嵌 | 两张卡牌翻面、相同则碰撞高亮、不同则并入时间线 |
| P6 | 结算页 | `/room/:code/result` | 结果标语、回合数、评级、词链回顾、`再来一局`、`回首页` |
| P7 | 规则弹层 | 全局 | 图文规则 + 反直觉案例（`猫` vs `猫咪` 不算） |

### 3.3 对局页（P4）布局

移动端竖屏为设计基准，自上而下：

```
┌─────────────────────────────┐
│ ←  第 3 / 15 轮       ⏱ 12s │  回合进度 + 倒计时环
├─────────────────────────────┤
│  锚点                        │
│  ┌────────┐ ┌────────┐      │  上一轮的两个词并列
│  │ 空调   │ │ 蝉     │      │
│  └────────┘ └────────┘      │
├─────────────────────────────┤
│  词链                        │
│  夏天 → 西瓜·冰棍 → 空调·蝉  │  横向滚动，点击看轮次
├─────────────────────────────┤
│  你想到了什么？              │
│  ┌─────────────────────┐    │
│  │ 热                  │    │  输入框，实时校验
│  └─────────────────────┘    │
│         [ 提交 ]             │
├─────────────────────────────┤
│  ● 你已提交   ○ 对方思考中   │  双盲状态指示
└─────────────────────────────┘
```

关键交互细节：

- **提交后输入框锁定并虚化**，直到下一回合开始。防止「提交后又改」造成状态不一致。
- **提交后不把自己的词回显到词链**——否则先交的人能从「我已上榜、对方未上榜」推断出对方必然不同，产生信息泄露。必须等 `round:reveal`。
- 倒计时最后 5 秒数字变红并轻微脉冲，**不放音效**（多人场景易打扰）。
- 20 秒很短，输入框进入页面即自动聚焦，减少一次点击。
- 键盘弹起后锚点区仍需保持可见（视口高度适配 `visualViewport`）。
- 「提前结算」需要明确反馈：对方提交的瞬间，倒计时环快速收拢并显示「对方已就位」，让玩家理解为什么时间突然没了。

### 3.4 结算页（P6）要点

- 成功：主视觉「两词相撞」动效，回合数大字号，评级徽章。
- 失败：不出现红色失败大字，中性色 + 「差一点点」，高亮「最接近的一轮」（启发式挑选，如字数相同或首字相同的轮次）。
- 词链回顾可横向滑动查看全部回合，每轮标注双方词与判定。
- `再来一局`：保持房间、重置状态，需双方都在结算页点击才开；仅一方点击显示「等待对方」。
- `回首页`：离开房间，触发房间销毁（若对方也已离开）。

## 4. 房间创建与邀请

### 4.1 创建

- P1 点「创建房间」→ P2 设置（可全默认直接确认）→ 后端创建 → 跳 P3。
- 房间码：**6 位**，字符集 `ABCDEFGHJKLMNPQRSTUVWXYZ23456789`（剔除 `I/O/0/1`），全局唯一，冲突则重生成（最多 5 次）。
- 房主拥有 `开始游戏`、`解散房间` 权限。无踢人功能（只有两人，没意义）。

### 4.2 邀请方式

| 方式 | 实现 | 场景 |
| --- | --- | --- |
| 复制链接 | `https://<domain>/room/ABC123` | 微信/QQ/任意 IM 粘贴 |
| 二维码 | 前端生成（`qrcode` 库），P3 展示 | 面对面扫码 |
| 房间码口述 | 首页输入 6 位码 | 语音通话、线下 |
| 系统分享 | `navigator.share()`，不支持降级为复制 | 移动端浏览器 |

邀请文案固定为：「我在玩接词挑战，来跟我撞个词 →」，不携带玩家真实身份信息。

### 4.3 加入

- 链接进入 → 自动带出房间码 → 显示对手昵称与房间设置 → 点「加入」入座。
- 首页输码 → 输入即校验，不存在/已满/已结束分别给出明确提示。
- 加入成功双方在 P3 实时看到席位亮起，**无需刷新**（依赖 WS 推送 `room:state`）。

### 4.4 房间生命周期

```
CREATED ──(第二人加入)──→ FULL ──(房主开始)──→ PLAYING
   │                        │                    │
   │                        │                    ├─(撞词/失败)→ FINISHED ─(再来一局)→ PLAYING
   │                        │                    └─(异常)→ ABORTED
   └──(TTL 2h)──→ CLOSED ←──(房主解散/双方离开)──┘
```

- `FINISHED` 保留 10 分钟用于「再来一局」，由 Redis TTL 控制。
- 所有状态变更由服务端写入并广播，**客户端不自行推断**。

## 5. 双人实时同步与轮次状态管理

### 5.1 服务端权威状态机

**唯一原则：房间状态只存在于 Redis，客户端是它的投影。** 客户端任何操作都是「请求」，不是「指令」。

```
                 ┌──────────┐
                 │ WAITING  │  等待第二人 / 等待房主开始
                 └────┬─────┘
                      │ game:start
                 ┌────▼─────┐
        ┌────────│ROUND_OPEN│ 回合开启，20s 倒计时，双方可提交
        │        └────┬─────┘
        │             │ 双方均已提交 或 20s 到期（服务端定时器）
        │        ┌────▼───────┐
        │        │ROUND_REVEAL│ 计算结果并同时下发，播 2s 动效
        │        └────┬───────┘
        │             │
        │      ┌──────┴───────┐
        │      │相同           │不同且未达上限
        │  ┌───▼────┐    ┌────▼─────┐
        └──┤FINISHED│    │ROUND_OPEN│（roundNo+1，锚点更新）
           │  WIN   │    └──────────┘
           └────────┘
                 ▲
                 │ 不同且达上限 / 放弃 / 房间异常
            ┌────┴─────┐
            │ FINISHED │
            │  LOSE    │
            └──────────┘
```

状态迁移全部由服务端定时器或消息驱动，**客户端不能直接触发 `ROUND_REVEAL`**。

### 5.2 双盲提交协议

这是防作弊与体验公平的核心。

1. 玩家提交 → 前端发 `round:submit { roundNo, word, clientSeq }`。
2. 服务端校验：房间状态、轮次号、玩家身份、词条合法性、历史词去重、幂等。
3. 校验通过 → 写入 Redis（`guess` 字段**对其他玩家永不广播**）→ 给该玩家回 `round:submit.ack`，向房间广播 `round:opponent_ready { playerId }`（**只报布尔状态，不带内容**）。
4. 双方均就位（或定时器到期）→ 服务端计算判定 → 一次性广播 `round:reveal { roundNo, words: {A, B}, isMatch }`。
5. 前端收到 `reveal` 才渲染卡牌。

**必须守住的三条线**：

- 对方词在 `reveal` 之前**绝不出现在任何下发给客户端的载荷里**——包括房间快照、重连接口、错误消息。抓包能看到就等于作弊。
- 自己的词在 `reveal` 前也**不回显到词链**，避免通过「我已上榜、对方未上榜」反推对方状态。
- 重连快照若发生在 `ROUND_OPEN` 中途，只返回「我方是否已提交」和当前轮次，**不返回任何一方本轮词**。

### 5.3 计时权威性

- 回合开始服务端记录 `roundDeadlineAt`（服务器时钟毫秒），随 `round:open` 下发 `serverNow`。
- 前端算 `offset = serverNow - Date.now()`，倒计时基于 `Date.now() + offset` 渲染，**不信任本地时钟**。
- 超时判定由服务端定时器负责，前端倒计时归零只是视觉表现，**不触发任何判定**。
- 双方提交后，服务端取消定时器并立即结算——前端收到的 `reveal` 会早于倒计时归零，这是正常路径。

### 5.4 断线重连

| 阶段 | 行为 |
| --- | --- |
| 检测断开 | WS 心跳超时（ping 10s / 超时 20s）→ 前端展示「重连中」遮罩 |
| 重连尝试 | 指数退避 1s/2s/4s/8s，最多 4 次 |
| 重连成功 | 携带 `token` 重新连接 → 服务端校验 → 下发房间快照 → 恢复 UI |
| 重连期间对局 | **不暂停**。已提交则正常推进；未提交则倒计时继续走 |
| 对手视角 | 显示「对方掉线了」，30 秒后出现「继续等待 / 结束本局」 |
| 结束本局 | 判 `ABORTED`，不计战绩，双方可立即重开 |

**[决策] 断线不暂停对局。** 暂停会带来「恶意断线拖延」漏洞，且实现复杂（双方同时断线、暂停期间计时冻结、恢复时序）。牺牲一点容错换规则简单——20 秒一回合，掉线重连回来大概率只丢一轮。

### 5.5 协议契约（前后端分离视角）

**职责划分**：REST 负责「进入房间之前」的操作，WebSocket 负责「进入房间之后」的全部实时交互。两者不重叠，避免同一份状态两条链路。

#### REST

| 方法 | 路径 | 请求 | 响应 |
| --- | --- | --- | --- |
| `POST` | `/api/rooms` | `{ nickname, maxRounds, anchorMode, startAnchor? }` | `{ code, playerId, token, settings }` |
| `GET` | `/api/rooms/{code}` | — | `{ exists, status, full, hostNickname, maxRounds }` |
| `POST` | `/api/rooms/{code}/join` | `{ nickname }` | `{ playerId, token, snapshot }` |
| `GET` | `/api/health` | — | `{ status, redis }` |

统一响应包 `{ code: 0, data, message }`，错误码：

`ROOM_NOT_FOUND` / `ROOM_FULL` / `ROOM_CLOSED` / `ROUND_MISMATCH` / `WORD_INVALID` / `WORD_REPEATED` / `NOT_YOUR_TURN` / `ALREADY_SUBMITTED` / `UNAUTHORIZED`。

#### WebSocket

连接：`ws://<host>/ws/game`，**连接后首帧发送 `auth`**（不把 token 放 URL，避免日志泄露）。

```json
{ "type": "auth", "token": "xxx" }
```

| 消息 type | 方向 | 载荷 | 说明 |
| --- | --- | --- | --- |
| `auth` | C→S | `{ token }` | 首帧鉴权，失败即断开 |
| `auth.ok` | S→C | `{ playerId, snapshot }` | 鉴权成功 + 全量快照 |
| `room.state` | S→C | `RoomSnapshot` | 任意状态变更后推送全量快照（简单可靠，优于增量） |
| `game.start` | C→S | `{}` | 仅房主可发，双方就位才允许 |
| `round.open` | S→C | `{ roundNo, anchor, deadline, serverNow }` | 回合开始 |
| `round.submit` | C→S | `{ roundNo, word, clientSeq }` | 提交 |
| `round.submit.ack` | S→C | `{ roundNo, ok, code? }` | 提交回执 |
| `round.opponent_ready` | S→C | `{ playerId }` | **只报状态，不带词** |
| `round.reveal` | S→C | `{ roundNo, words, isMatch, timedOut, nextAnchor? }` | 双方同时收到 |
| `game.finish` | S→C | `{ result, rounds, grade, chain }` | 终局 |
| `game.restart` | C→S | `{}` | 结算页重开（需双方确认） |
| `game.giveup` | C→S | `{}` | 主动放弃 |
| `player.offline` / `player.online` | S→C | `{ playerId }` | 在线态变更 |
| `error` | S→C | `{ code, message }` | 统一错误通道 |

`RoomSnapshot` 结构（**注意：绝不包含本轮任何一方未揭晓的词**）：

```json
{
  "code": "ABC123",
  "status": "PLAYING",
  "phase": "ROUND_OPEN",
  "roundNo": 3,
  "maxRounds": 15,
  "anchor": ["空调", "蝉"],
  "deadlineAt": 1762000000000,
  "players": [
    { "id": "p1", "slot": 1, "nickname": "小明", "online": true, "submitted": true },
    { "id": "p2", "slot": 2, "nickname": "小红", "online": true, "submitted": false }
  ],
  "chain": [
    { "roundNo": 1, "words": ["西瓜", "冰棍"], "isMatch": false },
    { "roundNo": 2, "words": ["空调", "蝉"], "isMatch": false }
  ],
  "myWordSubmitted": true
}
```

> `myWordSubmitted` 只告诉「我交没交」，不告诉「我交了啥」。前端自己存着本地输入即可。

### 5.6 幂等与并发控制

- **提交幂等**：Redis 的 `guess` Hash 以 `playerId` 为 field，重复写直接覆盖前先判断存在即返回上次结果，不产生副作用。
- **轮次栅栏**：每条 `submit` 必须携带 `roundNo`，与服务端当前轮次不符直接拒绝（`ROUND_MISMATCH`），防止旧请求「打进新回合」。
- **单房间串行**：同一 `code` 的写操作加本地锁（`ReentrantLock` + `ConcurrentHashMap` 按 code 分段），保证「双方同时提交」只触发一次判定。
- **限流**：单连接 10 消息/秒，超限断开；同 IP 建房 20 次/小时。

### 6.2 为什么是这套

1. **Vue 3 的响应式正好映射「服务端快照驱动 UI」这个模式。** 整个对局页只有一个 `roomStore`，收到 `room.state` / `round.*` 就整体替换，UI 自动跟着变。不需要为「倒计时、卡牌、词链」分别写状态同步逻辑，这是 Vue 相比手写 DOM 操作在这个场景里最大的收益。

2. **后端用 Spring 原生 WebSocket，不用 netty-socketio。** 这是个明确取舍：
   - `netty-socketio` 是社区对 Socket.IO 协议的 Java 实现，维护活跃度一般，与 Spring Boot 3 / Java 21 集成需要绕开自动配置，踩坑概率不低。
   - 10 人规模根本用不上 Socket.IO 的传输降级（长轮询兜底）、多路复用、房间 ACL 这些能力。
   - 原生 `TextWebSocketHandler` 干净、零第三方依赖，代价是要自己写重连、心跳、消息路由——合计约 150 行，比调试一个第三方库的兼容问题便宜。
   - 前端因此也不用 `socket.io-client`，直接 `new WebSocket()`，代码更少。

3. **Redis 作为唯一持久层，是这个 Demo 最合适的选择。** 房间态本身就是「短生命周期 + 强 TTL + 高频整块读写」的数据，跟 Redis 的 Hash + TTL 天然契合：
   - 不需要建表、不需要迁移、不需要 ORM，改字段就是改 JSON。
   - 房间 2 小时自动消失，省掉一个清理定时任务。
   - 10 人规模下，「用关系库存两个玩家的临时对局」纯属浪费。
   - 代价也说清楚：**没有事务、没有复杂查询、重启后数据可能丢**。Demo 完全可接受，V1 要存战绩时再加 Postgres。

4. **前后端分离 + Nginx 同域反代。** 前后端两个工程独立开发部署，但对外只暴露一个域名：`/` 走静态、`/api` 反代后端、`/ws` 升级 WebSocket。这样生产环境没有 CORS，也不用给 WS 单独配跨域白名单——只有本地开发（`localhost:5173` → `localhost:8080`）才需要开 CORS。

### 6.3 架构示意

```
┌──────────────────┐          ┌──────────────────┐
│  玩家 A 浏览器    │          │  玩家 B 浏览器    │
│  Vue 3 SPA       │          │  Vue 3 SPA       │
└────────┬─────────┘          └────────┬─────────┘
         │   HTTPS / WSS               │
         └─────────────┬───────────────┘
                       ▼
         ┌───────────────────────────┐
         │  Nginx（单域名同域反代）    │
         │  /      → 静态 dist/       │
         │  /api   → app:8080         │
         │  /ws    → app:8080 (升级)  │
         └─────────────┬─────────────┘
                       ▼
         ┌───────────────────────────┐
         │  Spring Boot 3 (Java 21)  │
         │  ├ RoomController  (REST) │
         │  ├ GameWebSocketHandler   │  ★ 权威状态机
         │  ├ RoundScheduler         │  20s 超时定时器
         │  ├ JudgeService           │  归一化 + 判定 + 去重
         │  └ RoomLockManager        │  按 code 串行
         └─────────────┬─────────────┘

         ┌─────────────▼─────────────┐
```

**关键点**：浏览器之间没有直连，所有词都过服务端。任何 P2P 方案（WebRTC DataChannel）在这里都是错的——它会让「服务端裁决」和「双盲」同时失效。

### 6.4 Redis 数据模型

单一持久层，全部用 Key 设计表达：

| Key | 类型 | 值 | TTL | 说明 |
| --- | --- | --- | --- | --- |
| `room:{code}` | String(JSON) | RoomSnapshot 主体 | 2h | 房间元信息 + 状态 + 玩家列表 |
| `room:{code}:guesses:{n}` | Hash | field=`playerId`, value=JSON `{raw,norm,timeout,at}` | 2h | **第 n 轮提交，不对外暴露** |
| `room:{code}:chain` | List | 每项 `{roundNo, words:[A,B], isMatch, timedOut}` | 2h | 已揭晓回合，追加写入 |
| `reconnect:{token}` | String | `{code}:{playerId}` | 24h | 重连映射 |
| `code:lock:{code}` | String | `1` | 2h | 房间码占用（`SETNX` 防碰撞） |
| `room:{code}:seq` | String | 轮次计数器 | 2h | `INCR` 生成 roundNo |

`room:{code}` 主体 JSON：

```json
{
  "code": "ABC123",
  "status": "PLAYING",
  "phase": "ROUND_OPEN",
  "roundNo": 3,
  "hostPlayerId": "p1",
  "maxRounds": 15,
  "anchorMode": "RANDOM",
  "anchor": ["空调", "蝉"],
  "deadlineAt": 1762000000000,
  "players": [
    { "id": "p1", "slot": 1, "nickname": "小明", "online": true, "submitted": false, "submittedRounds": [1, 2] },
    { "id": "p2", "slot": 2, "nickname": "小红", "online": true, "submitted": false, "submittedRounds": [1, 2] }
  ],
  "usedWords": ["夏天", "西瓜", "冰棍", "空调", "蝉"],
  "result": null,
  "createdAt": 1761999000000
}
```

- `usedWords` 用于**禁复用校验**，一次 `SMEMBERS`（或本地 Set）即可 O(1) 判断，避免遍历全部轮次。
- `submittedRounds` 保留用于结算页复盘与「我是否已提交」判断。
- `anchor` 存数组：第 1 轮是单元素（起始词），之后是上一轮的两个词。

**并发原子性**：`提交 → 校验 → 判断是否双方已交 → 触发结算` 这一串必须在一个锁内完成。Demo 用 `ReentrantLock`（按 `code` 分段）即可；要上多实例时换 Redisson 的 `RLock` 或 Lua 脚本。

### 6.7 关键实现点（易踩坑）

**1. 20 秒定时器与「提前结算」的竞态**

用 `ScheduledFuture` 按房间存一份。两条路径都可能触发结算：

- 定时器到期 → `settle(round)`
- 第二个玩家提交 → `settle(round)`

必须用 `AtomicBoolean settled`（按 round 维度）保证只结算一次，定时器在结算成功后 `cancel()`。否则会出现「超时结算完，第二个人又提交，触发第二次 reveal」。

**2. 服务重启后定时器丢失**

Redis 里的房间还在 `ROUND_OPEN`，但内存里的定时器没了 → 这一轮永远不结束。启动时扫描 `room:*`，对 `phase == ROUND_OPEN` 且 `deadlineAt < now` 的立即结算，未到期的重新注册定时器。**这是 Demo 也必须做的**，否则重启一次就卡死几个房间。

**3. `@ServerEndpoint` vs `WebSocketHandler`**

不要用 JSR-356 的 `@ServerEndpoint`——它每个连接新建实例，注入 Spring Bean 很别扭。用 `WebSocketHandlerRegistry` 注册 `TextWebSocketHandler`，单例 + 注入 Service，干净得多。

**4. 跨域与 WS 鉴权**

开发期前端在 5173、后端在 8080，需要 `WebSocketConfig.setAllowedOrigins("http://localhost:5173")`；生产走 Nginx 同域，留空即可。鉴权不放 URL query（会进 access log），放首帧 `auth` 消息。

**5. 消息序列化统一**

前后端所有消息都是 `{ "type": "...", "payload": {...} }` 两层结构。`type` 用常量类维护，前端 `protocol.ts` 手工对齐——虽然不如 protobuf 严谨，但 Demo 阶段加一层「type 白名单校验」就够，收到未知 type 直接丢弃并记日志。

### 6.8 部署（Docker Compose）

```yaml
services:
  redis:
    image: redis:7-alpine
    volumes: ["redis-data:/data"]
  app:
    build: ./backend
    environment:
      - SPRING_DATA_REDIS_HOST=redis
    depends_on: [redis]
  nginx:
    image: nginx:alpine
    ports: ["80:80"]
    volumes:
      - ./frontend/dist:/usr/share/nginx/html:ro
      - ./nginx.conf:/etc/nginx/conf.d/default.conf:ro
    depends_on: [app]
```

`nginx.conf` 关键两段：

```nginx
location /api/ { proxy_pass http://app:8080; }

location /ws/ {
    proxy_pass http://app:8080;
    proxy_http_version 1.1;
    proxy_set_header Upgrade $http_upgrade;
    proxy_set_header Connection "upgrade";
    proxy_read_timeout 3600s;   # 必须放大，否则 WS 被 60s 掐断
}
```

> `proxy_read_timeout` 默认 60 秒，不调会导致「对局中每隔一分钟莫名断线」，这是自建 WebSocket 最常见的坑。

## 9. 范围划分

### Demo（本次交付）

- 创建 / 加入房间（链接 + 房间码 + 二维码）
- 双人回合制对局，双盲提交，服务端判定
- **固定 20 秒/轮，双方提交即提前结算**
- **回合上限默认 15，建房时可自定义**
- 锚点接词、词链展示
- 超时弃权、主动放弃、结算页（成功/失败/中断）
- 断线重连、刷新恢复
- 规则弹层、移动端适配
- Docker Compose 一键起

- 战报分享图（词链可视化）

- 3 人以上房间（规则需重新设计，不是简单扩展）

## 10. Demo 阶段的刻意简化（技术债清单）

这些是为了快速验证玩法而主动砍掉的，**上线前逐条补**：

| # | 简化项 | 风险 | 补齐方式 |
| --- | --- | --- | --- |
| 1 | 无敏感词过滤 | 玩家可输入违规词，截图外传有风险 | 接入本地词库（Aho-Corasick），提交时校验 |
| 2 | Redis 单点，无持久化配置 | 重启丢全部对局 | 开 AOF `everysec`，或接受丢局 |
| 3 | 本地锁而非分布式锁 | 只能单实例部署 | 换 Redisson `RLock` 或 Lua 脚本 |
| 4 | 定时器在进程内 | 重启丢定时器 → 需启动扫描恢复 | 已实现启动恢复；多实例需改为 Redis 过期事件驱动 |
| 5 | 无账号，token 存 localStorage | 换设备/清缓存丢身份 | V1 接账号体系 |
| 6 | 无战绩持久化 | 玩完即焚，无法复盘留存 | V1 落 Postgres |
| 7 | 无监控告警 | 出问题只能看日志 | 接 Sentry / Prometheus |
| 8 | 前端协议类型手工同步 | 后端改字段前端可能漏改 | 生成 OpenAPI + 类型代码 |
| 9 | 无自动化测试 | 规则回归靠手点 | 至少给 `JudgeService` 写单测（判定边界表直接转用例） |

> 第 9 条建议不要省：`JudgeService` 的判定逻辑是最容易被后续改动破坏的地方，而 2.3 的边界表天然就是一组测试用例，写起来成本极低。
